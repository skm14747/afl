# Fix plan — SEO readiness, 24 Nov 2026

This plan closes every finding in `seo/audit-2026-11-24.md`, then checks the things that audit could not measure. It does not add translations, ratings, an author, or a second product.

The site is ready when all of these are true on a production build and on `https://astrologyforlove.com`:

1. `GET /robots.txt` is 200 and names the sitemap.
2. The soulmate title and description describe one birth chart.
3. The homepage emits `og:image`.
4. A draft locale such as `/es/compatibilidad-amorosa` has `noindex` in the HTML, `lang="en"` while the body is English, and a canonical on the English URL.
5. Every sitemap URL returns 200, one `h1`, one brand in the title, and an English canonical.
6. First Load JS is recorded. Any route over 150 kB is either reduced or written down with a reason.
7. Sign-pair URLs are not generated in bulk. A pair page ships only after the six items above, and only with its own copy.

## Keep these decisions

- English is the only published locale. `src/i18n/locales.ts` stays that way until a locale has real translated page copy.
- hreflang stays `en` and `x-default`. Do not advertise `es`, `fr`, `de`, `pt`, `hi`, `it`, `ja`, `id`, or `ar`.
- Child titles must not already end in `AstrologyForLove`. The root template adds `| AstrologyForLove`.
- No `FAQPage`, `AggregateRating`, `Review`, invented author, street address, or email.
- Do not merge synastry and birth-chart compatibility. They answer different queries.
- Do not put `params` back into `toolMetadata`. That helper is static on purpose so tool metadata does not wait on the request. Draft-locale robots belong on the locale layout, which already reads `params`.
- Calculator results stay browser-side. `astronomy-engine` stays the ephemeris.

## Phase 1 — Make robots.txt answer

**Why first.** A 500 on `/robots.txt` is the only critical finding. Google retries a 5xx robots file and can slow or pause crawling while it fails. The allow rule and the sitemap line never leave the server.

**Change.** Delete `public/robots.txt`. Keep `src/app/robots.ts`. Both files currently allow `/` and point at `https://astrologyforlove.com/sitemap.xml`. The App Router file is the one that can stay next to the sitemap route. The comments in the public file are not robots directives.

**Do not** add `Disallow` rules for `/es` or other drafts. Those URLs should stay crawlable and `noindex`, so Google can see the canonical. Blocking them in robots hides the noindex.

**Confirm on localhost.**

- `GET /robots.txt` returns 200.
- Body contains `User-agent: *`, `Allow: /`, and `Sitemap: https://astrologyforlove.com/sitemap.xml`.
- `GET /sitemap.xml` still returns 23 English URLs.

## Phase 2 — Make every title tell the truth

The Open Graph title is already closer to the page. The document title and meta description are the mismatch.

**Rewrite that layout.**

- Description: one chart, Venus, Moon, and Mars, what you look for in a partner. Say it is not a reading of two people.
- `ogTitle`: `Soulmate Calculator — AstrologyForLove`.

**On the page.** In the opening paragraph, add two plain links: synastry for two charts, and the moon-phase soulmate page for the two-date moon test. The visible disclaimer that this is not a named soulmate stays.

**Sweep the other 18 tool layouts before calling this phase done.** Compare each `title` and `description` in `src/app/[locale]/*/layout.tsx` with the `CalculatorShell` `title` and the number of birth forms. From the current source, soulmate is the one that claims a method the page does not run. The sweep is still required so a second mismatch is not left behind. A description may stay more specific than the `h1`. It may not name a second person, a synastry grid, or a Vedic score unless that page shows it.

**Confirm.**

- `/soulmate-calculator` title contains `AstrologyForLove` once and does not contain “synastry.”
- The HTML description matches the one-person form.

## Phase 4 — Put noindex in the HTML, and match lang to the words

**Why.** Middleware already sets `X-Robots-Tag: noindex, follow` for unpublished locales. Google honors that header. The HTML still has no robots meta, and `/es/...` is `lang="es"` while every sentence is English. A crawler that only reads the document, or a browser that picks a voice from `lang`, gets the wrong signal.

**Where.** `src/app/[locale]/layout.tsx` already awaits `params`. Add `generateMetadata` there, not inside `toolMetadata`.

- Published locale (`en`): `robots: { index: true, follow: true }`.
- Any other locale: `robots: { index: false, follow: true }`.

Keep the middleware header. Two signals are safer than one. Do not noindex `/` or unprefixed English URLs. The middleware treats a path with no locale prefix as `en`. After the change, curl `/` and confirm the header is absent and the meta says `index, follow`.

**Language.** Until a locale is published, the body is English.

- `lang` is `en` for draft locales.
- `dir` is `ltr` for draft locales, including `/ar`, because the sentences are English.
- When a locale is later flipped to `published` in `localePublicationStatus`, `lang` and `dir` follow that locale again, and this phase’s noindex branch stops applying.

Do not translate the message files in this phase. Publishing machine-translated copy would create nine indexable copies of the English site.

**Confirm.**

- `/es` and `/es/compatibilidad-amorosa`: `noindex, follow` in both the HTML meta and `X-Robots-Tag`. `lang="en"`. Canonical is the English URL. hreflang is still only `en` and `x-default`.
- `/love-compatibility`: no noindex header, `lang="en"`, title still has the brand once.
- `/ar` (or any other draft): `dir="ltr"` and `lang="en"`.

## Phase 7 — Sign-pair pages, only after Phases 1–6

This is the remaining content gap. It is also the easiest way to make the site worse. Seventy-eight near-duplicate “Aries and Leo” pages with swapped names will not be built.

**Gate.** Phases 1–6 are confirmed. `seo/keyword-clusters.json` still does not exist, and the volumes in `seo/competitor-gaps.md` were not re-measured. Do not treat those volumes as a build order.

**First batch, if it is built at all.** One route shape, for example `/zodiac-love/[pair]`, English only, in the sitemap, with a self-canonical. Start with the 12 signs linked from the existing zodiac guide, not all 78 ordered pairs. Each page needs:

- Its own title and description naming both signs.
- A unique opening that states the element and modality pair in words, using the compatibility method the love-compatibility calculator already uses.
- One `h1`.
- Links to `/love-compatibility`, `/zodiac-love`, and the two sign sections if those sections exist.
- No score that the page invents. If a score is shown, it is the same function the calculator calls.

**Stop the batch** if two pages can be told apart only by the sign names. Expand toward more pairs only after the first 12 are in the sitemap and a spot check shows unique openings.

Friendship, sexual, Chinese zodiac, “when will I meet someone,” progressed synastry, and a standalone Davison URL stay out. The composite page already explains Davison when birth times and cities exist.

## Phase 8 — Prove it on the public host

Localhost is not the crawl Google will do. After the code is deployed:

- `https://astrologyforlove.com/robots.txt` is 200 and lists the sitemap.
- `https://astrologyforlove.com/sitemap.xml` matches the localhost URL set.
- The homepage, `/soulmate-calculator`, `/love-compatibility`, and `/es/compatibilidad-amorosa` match the Phase 2–4 confirmations.
- Search Console is not part of this repo. Submit the sitemap there only if the property already exists. Do not invent indexing numbers.

- `FAQPage` rich results. Google retired those for most sites in May 2026. The visible questions on the calculators can stay.
- Star ratings, review counts, and a fake author.
- Merging synastry with birth-chart compatibility.
- A one-person “when will I meet someone” tool.
- Rewriting the Cosmic Hearts visual system. This plan does not change layout, color, or motion except where a sentence or a meta tag is wrong.
