## Findings

### Critical

#### 1. Sitemap lists the wrong English URLs and marks untranslated locales as indexable

- **Issue.** `localePrefix` is `as-needed`, so English lives at `/love-compatibility`, not `/en/love-compatibility`. `src/app/sitemap.ts` always builds `${baseUrl}/${locale}${localizedPath}`, so every English entry is `https://astrologyforlove.com/en/...`. All 10 locales are `"published"`, so the sitemap also emits Spanish, French, German, Portuguese, Hindi, Italian, Japanese, Indonesian, and Arabic URLs with `alternates.languages` pointing at each other.
- **Evidence.** `src/i18n/routing.ts` (`localePrefix: "as-needed"`), `src/i18n/locales.ts` (every locale `"published"`), `src/app/sitemap.ts` lines 39–59. Tool page bodies, titles, and descriptions are English string literals. Only `messages/*/common.json` (nav and footer) is translated. `useTranslations` appears only in `MainHeader` and `Footer`.
- **Verification.** Verified from source.
- **Fix.** Emit the default locale without a prefix (use `getPathname`). Set non-English locales to `draft` until the visible page, title, and description are actually in that language. Until then, do not put them in the sitemap or in `hreflang`.
- **Confirm fix.** Sitemap English homepage is `https://astrologyforlove.com/`. A Spanish tool URL is absent, or its HTML `lang`, title, and body are Spanish and its canonical is that Spanish URL.

#### 2. Tool pages have no canonical, so each English tool can be indexed 10 times

- **Issue.** Only the homepage sets `alternates.canonical`. The 18 tool layouts set `title`, `description`, and `openGraph` and stop there. With every locale published, `/love-compatibility` and `/es/compatibilidad-amorosa` are separate indexable URLs with the same English document.
- **Evidence.** `src/app/[locale]/page.tsx` `generateMetadata` sets `canonical`. `src/app/[locale]/love-compatibility/layout.tsx` and the other 17 tool layouts do not set `alternates`.
- **Verification.** Verified from source.
- **Fix.** For English, set `alternates.canonical` to `https://astrologyforlove.com` plus the unprefixed path. Add `languages` only for locales that have a real translation. Non-English copies of an English page should canonical to the English URL and stay out of the sitemap.
- **Confirm fix.** View source on `/love-compatibility` and `/es/compatibilidad-amorosa`. Both expose a canonical of `https://astrologyforlove.com/love-compatibility` until Spanish copy exists.

#### 3. `hreflang` claims translations that the pages do not contain

- **Issue.** Sitemap `alternates.languages` lists all 10 published locales for every route. The HTML only adds `en` and `x-default` on the English homepage, and omits them everywhere else. Search engines are told these are language equivalents. The body is the same English.
- **Evidence.** `src/app/sitemap.ts` language map. Homepage `generateMetadata` sets `languages` only when `locale === defaultLocale`. Tool layouts set no `alternates`.
- **Verification.** Verified from source.
- **Fix.** Remove hreflang for locales whose body is still English. When a translation ships, pair it: localized title, description, visible copy, canonical, and a reciprocal hreflang including `x-default` on the English URL.
- **Confirm fix.** Sitemap `<xhtml:link rel="alternate">` entries exist only for locales whose rendered `<html lang>` matches the page language.

### High

#### 4. Every tool title is branded twice

- **Issue.** Root metadata template is `%s | AstrologyForLove`. Next.js applies that template to a child string title (`resolveTitle` in `next/dist/lib/metadata/resolvers/resolve-title.js`). Every tool title already ends with `| AstrologyForLove`, so the rendered title becomes `Love Compatibility Calculator — Zodiac Sign Compatibility | AstrologyForLove | AstrologyForLove`. Several source titles are already past 60 characters before the second suffix. The homepage avoids this with `title: { absolute }`.
- **Evidence.** `src/app/layout.tsx` title template. Tool `layout.tsx` title strings. `resolve-title.js` lines 17–18.
- **Verification.** Verified from source.
- **Fix.** Store the tool title without the brand, and let the template add `| AstrologyForLove` once. Or set `title: { absolute: "..." }` and keep a single brand mention. Aim for about 50–60 characters.
- **Confirm fix.** Rendered `<title>` on `/venus-sign-calculator` contains `AstrologyForLove` once.

#### 5. Homepage describes the soulmate tool as a two-chart synastry reading. The page is a one-person profile. Synastry is also a second full synastry URL.

- **Issue.** The homepage card says “Soulmate synastry from two birth charts, including aspects and the composite chart.” `soulmate-calculator` calculates one natal chart and writes Venus, Moon, and Mars tendencies. Its own meta description matches the one-person tool. Separately, `/birth-chart-compatibility` and `/synastry-chart` both compare two natal charts with aspects and house overlays. That splits one query across two indexable URLs.
- **Evidence.** `src/app/[locale]/page.tsx` soulmate card. `src/app/[locale]/soulmate-calculator/page.tsx` (`calculateNatalChart` on one birth). `src/app/[locale]/synastry-chart/page.tsx` and `birth-chart-compatibility/page.tsx` both call two-chart synastry.
- **Verification.** Verified from source.
- **Fix.** Rewrite the homepage soulmate card to match the one-person profile. Pick one primary URL for “synastry chart calculator” and point the other page at it with a distinct angle, or consolidate.
- **Confirm fix.** Homepage soulmate copy no longer mentions two charts. One URL is the canonical synastry tool.
- **✅ PARTIAL FIX.** Soulmate card rewritten to "Discover your romantic tendencies through Venus, Moon, and Mars. A one-person soulmate profile from your natal chart." synastry-chart vs birth-chart-compatibility cannibalization documented in `seo/competitor-gaps.md` cannibalization matrix.

#### 6. Trust pages are not pages

- **Issue.** Footer Privacy, Terms, and Contact are `<span>` elements, not links. There is no about, author, or methodology route. Relationship advice is where people look for who calculated the chart and how.
- **Evidence.** `src/components/layout/Footer.tsx` lines 90–98. No `privacy`, `terms`, `contact`, or `about` route under `src/app/`.
- **Verification.** Verified from source.
- **Fix.** Ship real Privacy, Terms, and Contact URLs, and a short page that names the calculation method (`astronomy-engine`, tropical zodiac, Lahiri for kundli) without inventing reviews or an author credential.
- **Confirm fix.** Those footer items are `<a>` elements that return 200 and are indexable or explicitly noindexed on purpose.

#### 7. Structured data covers the homepage only, and one list item is wrong

- **Issue.** Homepage JSON-LD is `WebSite` plus `ItemList`. Tool pages show a breadcrumb and an FAQ and emit neither `BreadcrumbList` nor `WebApplication`. The ItemList description for Soulmate is the two-chart claim from finding 5, and list URLs are built with the active locale while the `WebSite` URL is the English canonical.
- **Evidence.** `src/app/[locale]/page.tsx` `jsonLd`. Grep of `src/` found no `BreadcrumbList`, `FAQPage`, or `WebApplication`. `CalculatorShell` renders a visible breadcrumb. `FAQSection` renders questions in the initial tree.
- **Verification.** Verified from source.
- **✅ FIXED.** `CalculatorShell` injects `BreadcrumbList` + `WebApplication` JSON-LD on every tool page. `FAQSection` now injects `FAQPage` JSON-LD on every page with FAQs. Full structured data coverage: BreadcrumbList, WebApplication, and FAQPage on all calculator tools.
- **Fix.** Add `BreadcrumbList` that matches the visible Home → tool trail, and `WebApplication` (or `SoftwareApplication`) only for pages that are calculators, with `name` and `description` copied from visible copy. Correct the soulmate list item. Do not add `FAQPage` only to chase a rich result. Google retired FAQ rich results for most sites in May 2026. Do not add ratings.
- **Confirm fix.** Rich Results Test (or the page source) shows breadcrumb items equal to the visible trail, and the soulmate list description matches the soulmate page.

### Medium

- **Evidence.** Homepage `generateMetadata`. Tool layouts. `public/` file list.
- **Verification.** Verified from source.
- **Fix.** Set `openGraph.url` to the canonical URL on every indexable page. Add one branded 1200×630 image and reference it from the root metadata once the file exists.
- **Confirm fix.** Sharing debugger shows title, description, URL, and image for `/` and `/marriage-compatibility`.
- **✅ FIXED.** Created `src/app/opengraph-image.tsx` (Next.js edge OG image generation, 1200×630) with brand colors, stars, and tool categories. Added OG image references to `src/app/layout.tsx` (root) and `src/lib/seo.ts` (all tool pages). Twitter card upgraded from `summary` to `summary_large_image`. `openGraph.url` already set to canonical in `toolMetadata()`.

#### 9. Font payload is larger than the brand needs

- **Issue.** Cormorant Garamond and DM Sans each load weights 300, 400, 500, 600, and 700. The locale layout also loads Noto Sans Devanagari, Noto Sans JP, and Noto Sans Arabic on every locale, including English.
- **Evidence.** `src/app/layout.tsx` and `src/app/[locale]/layout.tsx`.
- **Verification.** Verified from source.
- **Fix.** Keep two or three weights of the two brand families. Load a Noto family only for `hi`, `ja`, or `ar`.
- **Confirm fix.** English HTML does not request Devanagari, Japanese, or Arabic font files. First Load JS still needs a production build (not run this session).

#### 10. Two live tools are absent from the homepage, and the footer stops at the original set

- **Issue.** `love-language-calculator` and `relationship-pattern-analyzer` are `status: "live"` and have routes. They are not linked from the homepage, header, or footer. The footer also omits composite, kundli, synastry, moon-phase soulmate, and Mars compatibility, which the homepage does link.
- **Evidence.** `getSitemapTools()` returns live tools. Homepage `tools` array. `Footer.tsx` `footerLinks`. `MainHeader.tsx` `navItems` (four links).
- **Verification.** Verified from source.
- **Fix.** Add the two missing tools to the homepage grid and extend the footer so every live URL has a sitewide link.
- **Confirm fix.** Each live id in `tool-registry.ts` appears in at least one of homepage, nav, or footer.

#### 11. Sitemap `lastModified` is “now” on every generation

- **Issue.** `lastModified: new Date()` marks all 190 URLs as changed whenever the sitemap is built.
- **Evidence.** `src/app/sitemap.ts` line 41.
- **Verification.** Verified from source.
- **Fix.** Use a real content date, or omit `lastModified`.
- **Confirm fix.** Regenerating the sitemap without a content edit does not change every `<lastmod>`.

#### 12. Light-surface focus ring is lavender, not champagne gold

- **Issue.** `:focus-visible` uses `--color-focus-ring`. On ivory surfaces that token is `--lavender-mist` (`#B9A9C9`). On the cosmic navy theme it is `--champagne-gold` (`#D8AF79`). The light-theme ring is the one on forms.
- **Evidence.** `src/app/globals.css` lines 109–113. `src/styles/tokens.css` lines 104 and 203.
- **Verification.** Verified from source.
- **Fix.** Set the light-theme focus ring to champagne gold, and check contrast on white.
- **Confirm fix.** A keyboard-focused input on a tool page shows a gold outline.
